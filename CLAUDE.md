Real, non-trivial work — 3 separate categories of genuine bugs found and fixed, not a flag flip:

- **RARDLL calling-convention ABI mismatch, invisible on x64, a hard link failure on x86.** Both RAR-reading dependency pairs — `unrar-ng-sys`/`unrar-ng` (this project's own vendored fork, used for `.rar`) and `unrar_sys`/`unrar` 0.5.8 (pulled in transitively by `unarc-rs` for `.arj`, see the ARJ section above) — declared the RARDLL C API as `extern "C"` (cdecl) in their Rust FFI bindings. Reading the real vendored `dll.hpp` directly (not assumed) confirmed RARLAB declares every one of these functions `PASCAL`, which resolves to `__stdcall` on real Windows (the header's `#define PASCAL`/`CALLBACK` as empty only applies under `#ifdef _UNIX`). x64 has no cdecl/stdcall distinction at the ABI level, so this was completely invisible there; cross-compiling to i686 for the first time produced real `LNK2019: unresolved external symbol` errors, because MSVC decorates stdcall symbols as `_Name@N` on x86 while the Rust side was linking against the bare cdecl name — confirmed directly via `dumpbin /symbols` on the compiled `unrar.lib`, not inferred. Fixed by changing every affected `extern "C"` to `extern "system"` — Rust's standard, purpose-built idiom for exactly this (stdcall on Windows x86, identical to `extern "C"` everywhere else including x64) — across **4 vendored crates**: `vendor/unrar-ng-sys`, a newly-vendored `vendor/unrar-ng` (its own `extract_callback`/`callback` fn definitions needed matching), and a newly-vendored `vendor/unrar_sys` + `vendor/unrar` (the older 0.5.8 pair `unarc-rs` depends on, previously flagged in this doc's ARJ/Android section as "will need its own separate vendor patch" — that prediction was right, just triggered by x86 Windows before Android). All 4 wired into root `Cargo.toml`'s `[patch.crates-io]`. Verified as a real correctness fix, not just a link-time patch: ran the full 78-test core suite on i686 (including the password-protected real-WinRAR-fixture roundtrip, which exercises the callback path hardest) — all pass — **and** re-ran the full x64 suite unchanged afterward to confirm `extern "system"` is a genuine no-op there, per Rust's own documented semantics.
- **WiX fragment hardcoded `Win64="yes"`, silently building a mixed-bitness (invalid) MSI for x86.** `apps/desktop/src-tauri/windows/shell-context-menu.wxs` (this project's own FR-22 fragment, compiled by `candle.exe` *separately* from `main.wxs` — already documented above) hardcoded every `<Component>`'s `Win64` attribute to `"yes"`, written back when the project only ever built x64. Manually re-running `light.exe` directly (tauri-bundler's own error message just says "failed to run", no detail) surfaced the real WiX error: `ICE30`, duplicate/conflicting component registration from mixed 64-bit/32-bit components in one package. Fixed with the same `$(sys.BUILDARCH)`-conditional `<?if?>` block `main.wxs` (tauri-bundler's own generated file) already uses — confirmed by reading that real generated file, not guessed — since `sys.BUILDARCH` is scoped to the candle.exe *invocation* (its `-arch` flag), not to the file, it works correctly even though this fragment is compiled independently.
- **`tauri build --config` uses RFC 7386 JSON Merge Patch semantics — a differently-keyed resource map doesn't replace, it unions.** Building for i686 needs `bundle.resources` to point at `target/i686-pc-windows-msvc/release/...` instead of `target/release/...`, and `build.beforeBuildCommand` to add `--target i686-pc-windows-msvc`. Tauri has no per-target-triple config file convention (only per-OS: `tauri.windows.conf.json` etc.), so this needed an explicit `--config` override file — `apps/desktop/src-tauri/tauri.i686-pc-windows-msvc.conf.json`. First attempt just listed the new i686 resource paths as extra map keys — `tauri-cli` merges via the `json_patch` crate's RFC 7386 `merge()`, which is a recursive per-key patch: since the i686 paths were *different map keys* than the base config's x64 paths, both stayed, and `light.exe` correctly rejected the result (`ICE30` again, x64 and x86 copies of the same file both trying to install to the same path). Fixed by explicitly setting the 3 base x64 resource keys to JSON `null` in the override (RFC 7386: `null` deletes a key) alongside the 3 new i686 keys.
- **A real, still-not-fully-understood Cargo/build-script caching hazard, worked around rather than root-caused — flagged here so a future session doesn't lose hours to it again.** While iterating on the fixes above, directly invoking `cargo build --target i686-pc-windows-msvc -p vietzip-desktop` (bypassing `tauri build`) more than once caused the *already-correctly-built* `vietzip.exe`/`sfx-stub.exe`/`vietzip_shell_menu.dll` i686 binaries to silently revert to stale **x64** copies on disk (confirmed with `dumpbin /headers`, not assumed) — no error, no recompile message, just a wrong-architecture file reused from `target/i686-pc-windows-msvc/release/deps/`. Root cause not fully pinned down (suspected Cargo fingerprint/unit-cache confusion from mixing invocation styles — sometimes `-p pkg1 -p pkg2 -p pkg3`, sometimes `--manifest-path` for a single package, against the same target dir), but a `cargo clean --release --target i686-pc-windows-msvc` followed by building **all 4 needed packages in one single unified `cargo build -p ... -p ... -p ... -p ...` invocation** (never split across separate commands) produced a clean, fully-verified result every time it was tried this way. Separately confirmed: `vietzip-desktop`'s build script (`tauri_build::build()`) reads the *raw, unmerged* `tauri.conf.json` (x64 resource paths) unless invoked through `tauri build`, which sets a `TAURI_CONFIG` env var the build script explicitly watches (`cargo:rerun-if-env-changed=TAURI_CONFIG`) — so `cargo build -p vietzip-desktop` directly needs the x64 resource files to still exist on disk (for a resource-existence sanity check unrelated to the app's own compiled content) even when building for i686. **Practical rule going forward**: build i686 exclusively via `npx tauri build --target i686-pc-windows-msvc --config apps/desktop/src-tauri/tauri.i686-pc-windows-msvc.conf.json`, and if anything looks architecturally wrong, `cargo clean --release --target i686-pc-windows-msvc` and rebuild all 4 packages in one command before trusting the result — don't trust a fast "Finished in 0.5s" as proof nothing changed; verify architecture with `file`/`dumpbin` after any i686 build, every time.

Verified end-to-end the same way as every x64 MSI in this doc (query real compiled `File`/`Component`/`Extension` tables via `WindowsInstaller.Installer` COM, not installing): 13-file `File` table with correct sizes, 0 components carrying the `msidbComponentAttributes64bit` flag (confirms uniformly 32-bit, no repeat of the mixed-bitness bug), 0 `Permanent` components (clean uninstall), all 6 file associations present, unchanged from x64. Not yet installed on a real 32-bit Windows machine (none available in this environment, and — per the initial framing given to the user before this was attempted — genuinely rare in 2026: Windows 11 has no 32-bit edition at all, only Windows 10 and earlier).

### 7-Zip feature parity

By explicit user request, after a feature comparison against 7-Zip, scope grew past `ke-hoach-mvp.md` section 2/3's "ngoài phạm vi MVP" list. This section is the running checklist — keep both halves current as work happens; don't treat `ke-hoach-mvp.md` section 2/3 as still authoritative on its own without checking here first.

#### Done

- **AES-256 for `.7z`** (previously ZIP-only in the MVP table) — `sevenz_format.rs`.
- **FR-03 compression levels** (Fast/Normal/Ultra) — `CompressionLevel` in core, `--level` in the CLI, wired through the Tauri command, the Flutter bridge, and a real Desktop UI `<select>`.
- **FR-04 split/join, upgraded to real multi-volume parity** (`crates/core/src/split.rs`) — byte-level split into `<archive>.<ext>.001`/`.002`/... parts + join. Originally documented as "NOT true multi-volume ZIP/7z" (implementing a from-scratch binary format was judged too high-risk). **Corrected after verifying against real sources, not memory**: per 7-Zip's own SourceForge discussion threads, 7-Zip's own "Split to volumes" for *both* `.7z` and `.zip` is this exact same raw-byte-split technique — neither format has an internal multi-volume binary structure, and 7-Zip itself can't even read the real PKZIP spanning format (`.z01`/`.z02`/`.zip`) that WinZip/PKZIP use. So the byte-split mechanism here was already genuinely equivalent to 7-Zip, not a simulation. The one real UX gap — 7-Zip lets you open `.001` directly without a manual join step — is now closed: `split::resolve_if_split()` detects a `.001` path, joins into a temp file (named after `file_stem()` so the real extension survives for `Format::from_path` to recognize), and `lib.rs`'s `extract`/`list_entries`/`test_integrity` all call it transparently via a shared `with_resolved_archive()` wrapper (temp file cleaned up after use). Scoped to read-only entry points only — matches 7-Zip, which also can't edit-in-place on a split archive. CLI/Tauri/Desktop needed no new commands — the existing `extract`/`list`/`test` paths already benefit; Desktop's file-picker filters gained `"001"` so users can select a `.001` part directly. Verified with real roundtrip tests (`resolve_if_split_joins_transparently`, `extract_directly_from_first_part_without_manual_join`) plus a live CLI run (compress → split → delete original → `extract archive.zip.001` with no join step, content byte-verified).
- **FR-07 SFX self-extracting `.exe`** — `crates/sfx-stub` (standalone console binary, deliberately not Tauri/WebView2) + `crates/core/src/sfx.rs` (`write_sfx`/`extract_embedded_archive`, classic technique: archive bytes + a trailer appended after a valid stub PE — Windows' loader only reads up to the last section, so trailing data is safe). CLI: `vietzip sfx <archive> -o <out.exe>`. Desktop: `create_sfx` command + UI button. Verified with real generated `.exe`s actually executed (no-password extraction, correctly-rejected missing password, password + `--dest` override — all byte-for-byte content-verified).

- **Multi-threading, `.zip`'s own merge-based technique** (`zip_format.rs::compress_parallel`/`compress_single_folder`, shared core `compress_parallel_units`) — neither `zip` nor `sevenz-rust2` **0.7** (the version pinned at the time this was written) exposed an API to feed pre-compressed bytes into a writer or split a single file into independently-compressible blocks (confirmed by reading both crates' source, not guessed), so this ZIP-specific "compress each unit on its own thread into a temp archive, then merge by raw byte copy" technique was built instead — still ZIP-only, since it depends on `raw_copy_file`, an API `sevenz-rust2` doesn't have at all. **This is a different mechanism from `.7z`'s multi-threading below**: `.7z` doesn't use this merge trick — `sevenz-rust2` 0.17+ (adopted 2026-08-12, see "True block-level multi-threaded compression" under "Not done yet" below) parallelizes *inside* the LZMA2 codec itself, which is why it covers the single-huge-file case that this ZIP-side technique structurally cannot (a lone file has only 1 "unit" to spread across threads here). Instead, when compressing **≥2 top-level sources**, each is compressed independently on its own thread into a temp `.zip` (reusing the existing sequential path unchanged), then the temp archives are merged into the final output with `raw_copy_file` (byte copy, no re-compression — the same proven API `rewrite_archive` already uses for remove/rename, including with AES-256-encrypted entries). Safe by construction: each thread owns its own file, no shared mutable state; the merge step is a pure byte copy. **Extended 2026-08-12** to the case that was the documented gap — compressing a single large *folder* (not multiple sources): `compress_single_folder` treats that folder's direct children (`fs::read_dir`, ≥`PARALLEL_MIN_UNITS`) as the parallel units instead of `sources`, reusing the identical merge technique; the one difference is the folder's own directory entry (owned by no single worker) is written directly into the final writer via a `pre_directories` param before merging. Still only 1 level deep — a lone big *subfolder* inside that folder still walks its own tree sequentially on whichever thread drew it, and a single huge *file* still can't be split at all (hard API limit, unchanged). Verified with real tests (`parallel_compress_multiple_sources_matches_sequential_content`, `parallel_compress_preserves_password_across_merged_parts`, `parallel_compress_single_folder_with_many_children_matches_sequential_content`, `parallel_compress_single_folder_preserves_password`, `single_folder_with_one_child_falls_back_to_sequential`) plus a real CLI roundtrip (12-file folder + nested subfolder → compress → list → test → extract, content-verified).
- **Benchmark** (`crates/core/src/benchmark.rs::run_benchmark`) — compresses/decompresses a synthetic in-memory buffer (default 64MB) through both ZIP and 7Z, reporting MB/s and compression ratio; not a simulated CPU "rating" score like 7-Zip's own benchmark, just real throughput on this engine. - **Standalone single-file `.gz`/`.bz2`/`.zst`/`.xz` compress/extract** (`crates/core/src/single_format.rs`) — different from `.tar.gz`/`.tar.bz2`/`.tar.zst` (many files packed in a tar, then compressed): this compresses exactly 1 file directly, matching real `gzip`/`bzip2`/`zstd`/`xz` CLI behavior. `flate2`/`bzip2`/`zstd` were already dependencies (used for `.tar.*` extraction); `.xz` needed a new one, `lzma-rs` — deliberately chosen as a **pure-Rust** codec over `xz2`/liblzma-FFI-based alternatives, specifically to avoid repeating the C-library cross-compilation pain already hit once with `unrar-ng-sys` (see `vendor/unrar-ng-sys` below) — matters for this project since Android is still on the roadmap. Trade-off: `lzma-rs` doesn't expose a compression-level knob, so `CompressionLevel` (Fast/Normal/Ultra) has **no effect on `.xz` output** — different from every other format here, and its API shape also differs (`xz_compress`/`xz_decompress` process the whole stream in one call rather than exposing a lazy `Read`, handled with a small `CountingSink` writer for the size-only cases like `list_entries`/`test_integrity` so nothing gets buffered in memory). All 4 formats reject multiple sources or a directory source with a clear error, matching real single-file-compressor semantics — these aren't container formats. `Format::from_path` checks `.tar.gz`/`.tar.bz2`/`.tar.zst` before the bare `.gz`/`.bz2`/`.zst`/`.xz` suffixes so the two don't get confused. CLI/Desktop/Tauri needed **almost no new wiring** — the existing generic `compress`/`extract`/`list`/`test` commands already dispatch through the expanded `Format` enum; only the Desktop file-picker filter list needed `xz`/`txz` added (`gz`/`bz2`/`zst` were already there). Verified with real roundtrip tests per format plus a rejection test for each invalid-input case.
- **`.tar.xz` extraction** (`tar_format.rs::spool_xz_to_tar`) — `lzma-rs`'s eager whole-stream API doesn't fit `tar_format.rs`'s lazy-`Read`-based decoder pattern the way `flate2`/`bzip2`/`zstd` do, so this fully decompresses the `.xz` layer to an anonymous `tempfile::tempfile()` first (deleted automatically on close, safe on Windows — no `TempDir` guard lifetime to manage since the `File` handle itself is boxed straight into the `Box<dyn Read>`), then treats that spooled file exactly like a plain `.tar`. - **Broader "extract-only" format coverage, wave 1: `.cab`/`.cpio`/`.deb`/`.rpm`** — by explicit user request to cover 7-Zip's full extract-only format list (previously a deliberate non-goal, reversed 2026-08-12). Each backed by a real, actively-maintained, permissively-licensed crate (verified via real vendored source, not docs summaries alone) rather than hand-rolled parsing:
  - `.cab` (`cab_format.rs`) — crate `cab` (MIT, pure Rust). Supports Uncompressed/MSZIP/LZX (not Quantum, an old/rare InstallShield-era scheme — the crate itself reports this clearly if hit, not a silent misread). CAB has no real directory-entry concept; `\`-separated names are normalized to `/` and parent dirs are created on the fly during extract.
  - `.cpio` (`cpio_format.rs`) — crate `cpio` (MIT), `newc`/SVR4 variant only (the modern, actually-common one — Linux initramfs, RPM payloads; older `odc`/binary cpio is legacy and out of scope, crate reports a clear magic-number error if hit). Sequential entry-by-entry API, different shape from the "open once, random access" APIs of zip/cab — `extract`/`list_entries`/`test_integrity` each drive their own loop rather than sharing a common open helper.
  - `.deb` (`deb_format.rs`) — **not a real container format of its own**: it's a plain Unix `ar` archive (crate `ar`, MIT, same author as `cab`) holding exactly 3 members (`debian-binary`, `control.tar.*`, `data.tar.*`). Rather than showing all 3 flat the way 7-Zip's raw `ar`-view does (forcing a second manual "open" step into `data.tar.*`), this module finds `data.tar.*` itself, spools it to a temp file with the right extension (same `tempfile`-spool technique as `.tar.xz`), and hands it straight to the already-verified `tar_format.rs` — so a `.deb` behaves as 1 unified format from the user's side, matching this project's minimalism stance (NFR-11) over strict 7-Zip parity. `control.tar.*`/`debian-binary` (install scripts/metadata, not user-facing content) are intentionally not surfaced.
  - `.rpm` (`rpm_format.rs`) — crate `rpm` (Apache-2.0/MIT). Deliberately uses the crate's **streaming** API (`PackageReader`/`next_file`), not the simpler `Package::open`/`Package::files()`, because the simple path loads the entire compressed *and* decompressed payload into a `Vec<u8>` — a direct conflict with this project's established >1GB-safe streaming discipline (DoD #4). `list_entries` is even cheaper: `PackageMetadata::open` + `get_file_entries()` reads sizes/paths straight from the header without touching the payload archive at all. The `rpm` crate's `xz-compression` feature was deliberately excluded from `Cargo.toml` — it pulls in `liblzma` (C FFI), which would break the pure-Rust-codec precedent already set in `single_format.rs` for the exact same reason (Android cross-compile risk, see `unrar-ng-sys`); `.rpm`s using XZ payload compression (common on openSUSE) will report a clear error rather than silently misreading — gzip/zstd/bzip2 (the other common cases) work normally. A real path-traversal guard was needed here specifically: RPM stores absolute install paths (e.g. `/usr/bin/hello`), and naively `Path::join`-ing an absolute path onto `dest_dir` **replaces** `dest_dir` entirely per Rust's own `Path::join` semantics — `relative_path()` strips `RootDir`/`ParentDir`/`Prefix` components before joining, closing a real traversal vector, not just a theoretical one.

- **FR-17 Repair/recovery of damaged archives** (`crates/core/src/repair.rs::repair`, CLI `vietzip repair <archive> -o <dest>`) — done 2026-08-12, scoped exactly to what the spec's own wording allows ("mức độ hỗ trợ tùy định dạng" — support level varies by format), not evenly across formats:
  - **ZIP gets real data recovery.** The common real-world corruption case is the central directory (the index `ZipArchive::new` needs, always at the *end* of the file) being missing/truncated — e.g. a copy or download interrupted after file data was written but before the trailer — while each entry's own local file header (signature `PK\x03\x04`) and data earlier in the file are still intact and independently readable. This is exactly what the `zip` crate's own public streaming API, `zip::read::read_zipfile_from_stream`, is for — reused as-is rather than hand-rolling a ZIP parser (the project has already twice declined that risk for the multi-threading feature, see above). When an entry's local header itself doesn't parse (`Err`, not just `Ok(None)`/EOCD), a byte-by-byte scan resumes from the next `PK\x03\x04` signature onward, so 1 damaged entry doesn't sink every entry after it. Each entry is spooled to an anonymous temp file first (bounded disk, not memory — same trade-off as `tar_format.rs`'s `.tar.xz` spooling) and only committed into the rebuilt archive if it read back **fully and correctly** (CRC intact); anything that fails partway is dropped, never written half-corrupt. A fast path (`try_already_healthy`) skips the whole scan and just byte-copies the file when it turns out to already open and test fine — avoids pointless recompression and preserves existing encryption exactly.
  - **A real, hard API limitation surfaced by writing an actual test, not by reading crate docs**: encrypted (AES/ZipCrypto) entries — and separately, entries using a streaming "data descriptor" — are rejected by `zip`'s own `ZipFileData::from_local_block` *before* even the filename is parsed out of the header (confirmed by adding temporary `eprintln!`s and watching the exact error fire mid-header, not assumed from the source read). So the raw-scan technique can't even discover these entries' *names*, let alone recover their content — they're silently absent from both `recovered` and `unrecoverable` in `RepairReport`, documented plainly in the module doc rather than glossed over. This only matters for archives that are *both* encrypted *and* structurally damaged — an already-tiny, inherently-hard intersection (that's what encryption is for).
  - **`.7z` gets detection only, honestly, not pretend-repair**: `sevenz-rust2` has no equivalent "read past a damaged header" API — `.7z`'s header describes solid-block/folder structure shared across entries, so a damaged header generally means the boundaries between files are gone, not just the index. `repair()` tries a normal open; if it succeeds, byte-copies (same fast path as ZIP); if it genuinely fails, returns a clear error saying so rather than emitting a misleadingly "successful" empty archive.
  - All other formats (RAR/TAR-family/CAB/CPIO/DEB/RPM/single-file) return `Error::UnsupportedOperation`, same as `add_entries` already does for non-ZIP — this project doesn't write those formats at all, so "repair" (produce a new file) has no meaning for them.
  - Verified with 5 real tests exercising genuine corruption, not synthetic mocks: a real archive with its EOCD/central-directory bytes truncated off (recovers all entries); a real archive with 1 entry's compressed-data bytes XORed to garbage mid-file, verifying the other entries around it still recover; the encrypted-entry gap above (confirmed the entry never leaks into either report list, and the repaired output genuinely doesn't contain the secret content); the already-healthy fast path (byte-identical copy); and a non-ZIP garbage file (clean error, no empty `dest` file left behind). Plus a real CLI roundtrip end-to-end (`compress` → truncate the real file's central directory via a PowerShell EOCD parse → `test` correctly fails with "Could not find EOCD" → `repair` → repaired file passes `test` → `extract` gives back the exact original byte content) and a real `.7z` healthy-archive smoke test through the CLI.
  - **Wired into Desktop UI 2026-08-12** (was core+CLI only when first done): `repair_archive` Tauri command + a "Sửa file nén bị lỗi..."/"Repair damaged archive..." button in the Advanced section (same pattern as Convert/Checksum), result summary (`recovered`/`unrecoverable` counts) shown inline below the button, both locale files updated. Verified via `npm run build` (TS+Rust compile clean) and a plain Vite dev-server visual check (button renders, 5-column layout intact) — real Tauri IPC/native-window behavior not exercisable in this environment, same documented gap as every other Tauri-only feature here.

- Capabilities/permissions live in `src-tauri/capabilities/default.json` — a new Tauri plugin's permission (e.g. `"dialog:default"`) must be added there or it silently fails at runtime with a permission-denied error, not a compile error. Custom `#[tauri::command]` functions (everything in this project's own `lib.rs`) do **not** need capability entries — only built-in plugin commands do.
- Package/crate renamed from the `create-tauri-app` scaffold defaults to `vietzip-desktop`/`vietzip_desktop_lib` across `package.json`, `src-tauri/Cargo.toml`, `src-tauri/src/main.rs`, `tauri.conf.json`'s `productName`/window `title` — keep these in sync if renaming again.
- **WiX/MSI is codepage 1252** — non-Latin-1 characters (Vietnamese diacritics) in strings that end up in the MSI database (`fileAssociations` `name`/`description`, shell-verb labels) fail the build outright. Keep those specific strings ASCII-only; regular app UI text has no such restriction (webview, UTF-8 throughout).

### Shell context-menu integration (FR-22)

**Windows (MSI only)**: `apps/desktop/src-tauri/windows/shell-context-menu.wxs` is a WiX **Fragment**, wired in via `tauri.conf.json`'s `bundle.windows.wix.fragmentPaths`/`componentGroupRefs` (`WixConfig::fragment_paths` in `tauri-utils`; `main.wxs`'s own `{{#each component_group_refs}}` block). It registers `HKCR\SystemFileAssociations\.<ext>\shell\...` verbs (not the FR-23 ProgIds, to avoid ID-ownership conflicts) whose commands invoke a bundled `vietzip.exe` (CLI) at `[INSTALLDIR]vietzip.exe`. The CLI itself gained the logic these verbs need: `Compress`'s `-o` is optional (auto-derives `<source-name>.zip` — `derive_compress_output()`), `Extract` gained `--here`/`--to-subfolder` (`extract_dest()`) — both covered by real temp-file-roundtrip unit tests in `context_menu_tests`. Verified by querying the **compiled MSI's** `Registry`/`File` tables read-only via the `WindowsInstaller.Installer` COM object (MSI SQL has no `LIKE` — fetch all rows, filter client-side), not just the pre-compile template.

Some WiX/candle mechanics that aren't obvious and are easy to get wrong:
- `<Component>` supports a `Directory` attribute directly (confirmed in the real WiX 3.14 `wix.xsd`, not assumed), and `<ComponentGroup Directory="INSTALLDIR">` can hold `<Component>` elements directly — no `<DirectoryRef>` wrapper needed inside a `<Fragment>`.
- Each `.wxs` file passed to `tauri-bundler` is compiled by `candle.exe` **separately** (once per file, not once for all inputs) — a `<?define Win64="yes"?>` in `main.wxs` is invisible to a fragment file compiled independently, so cross-platform-shared fragments must hardcode `Win64="yes"` rather than referencing `$(var.Win64)`.
- `bundle.resources` (top-level, shared across all platforms) is a `source -> dest` map; `bundle.linux.deb.files` is the **opposite**, `dest -> source` — confirmed by reading `tauri-bundler`'s real `copy_custom_files` implementation, not assumed. Getting this backwards silently produces a broken/empty package.
- Glob entries in `bundle.resources` (Map form): a value of `""` places every matched file flat at the resource root, keeping its own filename (`dest.join(path.file_name())`) — this is how `vietzip.*`/`sfx-stub.*` avoid a platform-specific `.exe` hardcode while still landing next to the main binary the way `current_exe().parent().join(...)` expects. An empty glob match, or a literal path that doesn't exist, is a hard build error (`GlobPathNotFound`/`ResourcePathNotFound`) — every resource entry must resolve on every platform that builds from this config.
- A broad glob like `vietzip*` will also match `vietzip-desktop.exe` (the main app binary, same directory, same prefix) — WiX's ICE30 validation then fails ("installed by two different components"). Use `vietzip.*` (literal dot) to require a dotted extension and exclude the dash-prefixed sibling.

**Linux**: `apps/desktop/src-tauri/linux/vietzip-nautilus.py` (Nautilus Python extension, 3 actions) + `postinst.sh` (restarts Nautilus), wired via `bundle.linux.deb.files`/`recommends`/`postInstallScript`. Only `.deb` gets this — AppImage is portable/no-install-step, so there's no natural hook to register a Nautilus extension from one. See `linux/README.md` for the GTK3-vs-GTK4 method-signature risk (unverified — no Linux test environment).

**macOS**: `apps/desktop/src-tauri/macos/quick-actions/*.workflow` (3 Automator Quick Actions calling the `vietzip` CLI) + `install-quick-actions.sh`. Materially lower confidence than Windows/Linux — neither buildable nor testable here at all, so unlike Windows (real MSI, queried tables) or Linux (source-verified bundler config), **the `.workflow` plist content is only confirmed to be well-formed XML**; Automator-specific semantic correctness (right keys, right types) is unverified. See `macos/README.md` for a guaranteed-correct manual-recreation fallback via Automator's GUI.

**SFX bundling**: `sfx-stub.exe` and the CLI's `vietzip.exe` are bundled as `bundle.resources` (landing in `INSTALLDIR` alongside the main binary, confirmed via the compiled MSI's `File` table) and `beforeBuildCommand` runs `cargo build -p vietzip-sfx-stub -p vietzip && npm run build` so both are compiled automatically before `tauri build` packages them.

## Core engine architecture

`crates/core/src/lib.rs` defines a `Format` enum (detected from file extension via `Format::from_path`) and dispatches `compress`/`extract`/`list_entries`/`test_integrity` to one format-specific module per codec family:
- `zip_format.rs` — ZIP via the `zip` crate; only format supporting password/AES-256 (FR-05). Named `zip_format`, not `zip`, to avoid colliding with the external `zip` crate at the crate root.
- `sevenz_format.rs` — 7Z via `sevenz-rust2` (maintained fork; the original `sevenz-rust` is unmaintained). Read+write, LZMA2 default. AES-256 via the crate's `aes256` feature, always paired with `set_encrypt_header(true)` (hides the file list too, not just content). `content_methods` order: last vec element applies to plaintext first, first element closest to disk — `[AES, LZMA2]` (compress-then-encrypt), confirmed against the crate's own `examples/advance.rs`.
- `tar_format.rs` — extraction-only (no `.tar*` creation in MVP scope) for `.tar`/`.tar.gz`/`.tar.bz2`/`.tar.zst`, layering `flate2`/`bzip2`/`zstd` under the `tar` crate.
- `rar_format.rs` — **extraction-only, forever** (FR-02/FR-14/LICENSES.md) via `unrar-ng` (FFI to RARLAB's vendored UnRAR C++ source). `compress()` never routes here — `Format::Rar` only appears in `extract`/`list_entries`/`test_integrity` dispatch, so no code path can accidentally write a `.rar`. Switched from the original `unrar` crate to `unrar-ng` (API-compatible fork, same license) because `unrar`'s build script doesn't cross-compile to Android at all.
- `split.rs` — byte-level split/join (FR-04, see above).
- `sfx.rs` — SFX trailer format (FR-07, see above).
- `error.rs` — shared `Error` enum (thiserror) with a shared `Error::io(path, source)` constructor.

Every format module maps its underlying crate's error/password variants onto the shared `Error::PasswordRequired`/`Error::WrongPassword`, so callers get consistent behavior regardless of archive format.

### `vendor/unrar-ng-sys` — locally patched dependency

`unrar-ng-sys` 0.7.7's `build.rs` decides which vendored UnRAR `.cpp` files to compile using `cfg!(windows)` — the **host**, not the **target** — so cross-compiling to Android from Windows tried to compile Windows-only files (`isnt.cpp`, `motw.cpp`) and failed. The crate correctly uses `CARGO_CFG_TARGET_OS` elsewhere in the same file, just not for this file-selection logic.

Fix: `vendor/unrar-ng-sys/` is a copy of the crates.io source with `build.rs` patched (~10 lines) to read `CARGO_CFG_TARGET_OS`/`CARGO_CFG_TARGET_ENV` instead, wired in via `[patch.crates-io]` in the root `Cargo.toml`. No behavior change on Windows (full test suite re-verified). User explicitly approved vendoring this before it was done — a real maintenance commitment, not a trivial tweak. Check upstream (`github.com/ttys3/unrar.rs`) periodically; drop the patch if a future release fixes it natively.

## What the plan describes

`du-an-nen-giai-nen.md` (Vietnamese) is a product/technical plan for a free, open-source, cross-platform archiver positioned as a WinRAR/7-Zip alternative for Vietnamese users. Key constraints that drive any implementation work:

- **RAR: extraction only, never creation.** The project never creates/writes `.rar` (needs a commercial RARLAB license) — compression targets are open/royalty-free only: `.zip`, `.7z`, `.tar`(+`.gz`/`.bz2`/`.zst`). Extraction is broader and includes `.rar` (read-only) via a license-vetted extraction-only library — see FR-02, FR-14, section 7.
- **License hygiene is a hard requirement for anything that creates/writes archives** (NFR-08): must be public-domain/BSD/MIT/zlib/LGPL or similarly unencumbered. RAR-reading is the one deliberate, narrowly-scoped exception, kept isolated from write-capable codec modules.
- **Proposed architecture**: platform UIs (Desktop, Mobile, Shell Extensions, CLI) all call into one cross-platform core engine owning codecs, format parsing, AES-256, and streaming I/O. UI layers stay thin; all compression logic lives in the shared core.
- **Minimalism is a first-class UI constraint** (NFR-11): a few large toolbar buttons, a file list, a status bar. Advanced options hidden behind a secondary section, never on the main screen. Right-click context menu stays to 2-3 top-level items, no deep submenu nesting.
- **Bilingual Vietnamese/English from v1.0** (FR-30–32) via key-value language files so community translations don't require code changes. Full Unicode support for Vietnamese diacritics in filenames is mandatory.
- Full FR-01…FR-36/NFR-01…NFR-11 list, tech stack per component, and the phased roadmap (Giai đoạn 0–10) live in the document — consult it directly rather than duplicating here; it's the source of truth for scope. FR numbers were renumbered when FR-14 (RAR) was inserted — don't assume a number from memory.
- **Execution order deviates from the phased roadmap**: per `ke-hoach-mvp.md`, actual build order is Core engine → CLI → Desktop via Tauri, **sequentially Windows → Linux (Ubuntu) → macOS** (reprioritized from an earlier "all 3 Desktop OSes as one bundled phase," itself already reprioritized once from an even earlier Android-first plan) → Android → iOS. See "Status by platform" above for exactly where each platform stands. MVP scope was originally narrower than the full spec — check `ke-hoach-mvp.md` section 2/3 before assuming an FR is in scope, though see "7-Zip feature parity" above for what's since been added by explicit request.
